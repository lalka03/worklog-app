# Worklog Yandex Test operations

Deployment requires owner approval of the exact resource names, cloud, pilot and backup folder IDs, region, projected costs and limits, and public HTTPS gateway exposure. Use a dedicated pilot folder for the app, gateway and YDB, and a separate backup-only folder in the approved cloud for the private backup function, timer, bucket and key. Keep application and legacy functions out of the backup-only folder. Use synthetic data during setup. Record the existing `worklog-api` function ID, public flag, latest version ID and trigger/bucket bindings before and after setup. Verify that the IDs, settings and prior backup path still match. Keep the Firebase projects, #28 APK and its backend outside this rollout.

## Setup order

Allow about 30 minutes of hands-on time for the first setup if the CLI and billing account are ready. Resource provisioning and build jobs can add elapsed time.

1. Create a YDB Serverless **OLTP** database in the approved pilot folder. Save the endpoint and database path separately from the connection details (`grpcs://…:2135` and `/region/folder-id/database-id`). Run `backend/schema.yql` in the YDB console with a schema operator. Give runtime identities no access to other databases. [Creating a serverless database](https://yandex.cloud/en/docs/ydb/operations/manage-databases) · [Connecting from a function](https://yandex.cloud/en/docs/ydb/tutorials/connect-from-cf)
2. In the backup-only folder, create a dedicated standard-class private Object Storage bucket for `yandex-test/`. Set **Read objects**, **Read object list** and **Read settings** to **With authorization**. Leave versioning off for this disposable pilot so object expiration can remove old payloads. Enable default bucket encryption with a new symmetric KMS key approved for this pilot. Set a lifecycle rule filtered to prefix `yandex-test/` with expiration at 30 days. The equivalent AWS CLI configuration is in `cloud/backup-lifecycle.json`. Confirm the rule in bucket settings after applying it. Keep key versions available through the last backup's lifetime. [Bucket encryption](https://yandex.cloud/en/docs/storage/operations/buckets/encrypt) · [Lifecycle operations](https://yandex.cloud/en/docs/storage/operations/buckets/lifecycles)
3. Bind the following identities only to the indicated pilot resources. Keep operator permissions separate and time-limited.

   | Identity | Scope and permissions |
   |---|---|
   | Gateway invoker | `functions.functionInvoker` on the private application function |
   | App runtime | `ydb.editor` on the pilot database only |
   | Backup timer invoker | `functions.functionInvoker` on the backup-only folder containing the target function |
   | Backup runtime | `ydb.viewer` on the specific database in the pilot folder, `storage.uploader` and `storage.configurer` on the dedicated backup bucket, and `kms.keys.encrypter` on its KMS key |
   | Restore operator identity | `ydb.editor` on the disposable restore database, `storage.viewer` and `storage.configurer` on the dedicated backup bucket, and `kms.keys.decrypter` on its KMS key |

   Grant backup runtime access across folders by binding its identity to the specific pilot YDB database. The gateway invoker is scoped to the app function in the pilot folder. Review inherited folder and cloud grants. Encrypted object operations require `storage.configurer` on the dedicated bucket and the corresponding KMS key role. The bucket grant includes policy and lifecycle configuration permissions, so keep this bucket dedicated to the Worklog backup. Use the provisioning operator to set the bucket policy and lifecycle. Smoke-test encrypted upload and restore with their respective identities on synthetic data and recheck bucket privacy and retention. Stop deployment if bucket-scoped `storage.configurer` is unavailable or the smoke test fails. A folder- or cloud-level storage grant is outside this deployment plan. [Functions IAM](https://yandex.cloud/en/docs/functions/security/) · [YDB IAM](https://yandex.cloud/en/docs/ydb/security/) · [Object Storage IAM](https://yandex.cloud/en/docs/storage/api-ref/authentication) · [Encryption permissions](https://yandex.cloud/en/docs/storage/concepts/encryption)
4. Build separate Python 3.12 ZIPs from the reviewed commit. Put `backend/requirements.txt` at ZIP root as `requirements.txt` and the required backend modules under `backend/`. For the application ZIP include `backend/{index,security,service,store}.py` and a root `index.py` containing `from backend.index import handler`. For the backup ZIP include `backend/{backup,security,service,store}.py` and a root `index.py` containing `from backend.backup import handler`. Set the entry point for each function to `index.handler`, select its own runtime service account, and set `WORKLOG_YDB_ENDPOINT` and `WORKLOG_YDB_DATABASE` from step 1. Deploy the private application function in the pilot folder and the private backup function in the backup-only folder. The app uses metadata IAM credentials and the backup uses the short-lived IAM token supplied by the function context. Exclude tests, APKs, credentials and logs from the packages. [Python invocation context](https://yandex.cloud/en/docs/functions/lang/python/context)
5. In the backup-only folder, create the timer with the backup timer invoker identity. Set the timer target to the private backup function ID in that folder and verify that the invoker has the required folder-level binding. Set `15 10 ? * * *` for daily 10:15 UTC. Configure the backup function with `WORKLOG_BACKUP_BUCKET`, `WORKLOG_BACKUP_KMS_KEY_ID`, and `WORKLOG_BACKUP_TRIGGER_ID` from that timer. Start the backup with 512 MB RAM and a 120-second timeout and record actual duration and memory in the synthetic rehearsal. Check for the first completed backup before opening the pilot. Configure an alert on backup failures or timeouts and check daily for a manifest younger than 26 hours. A failed manifest write leaves an uncommitted object that expires with the same policy. [Timer format and IAM](https://yandex.cloud/en/docs/functions/concepts/trigger/timer) · [PutObject and encryption headers](https://yandex.cloud/en/docs/storage/s3/api-ref/object/upload)
6. After unit and negative tests pass and public exposure is approved, substitute the new private function ID and gateway invoker service account ID in `cloud/gateway.yaml`. Publish the gateway over HTTPS. The private backup function has no gateway route. For a protected request send `X-Worklog-Authorization: Bearer …`, leaving the gateway to handle its IAM authorization separately. Test CORS with the Capacitor origin and its actual request headers. [Gateway Cloud Functions integration](https://yandex.cloud/en/docs/api-gateway/concepts/extensions/cloud-functions)
7. From a trusted operator shell, connect `YdbStore.connect(endpoint, database, credentials)` with short-lived pilot DB operator credentials and call `inv = seed_owner_invite(store)` from `backend.service`. Deliver `inv["code"]` only to the verified owner through a private channel. Keep `inv["id"]` for setup. An unredeemed bootstrap invite can be replaced by repeating the operation. After the owner registers, verify the account UID and invite consumption against the trusted operator's records, then call `promote_owner(store, uid, inv["id"])`. The owner signs in again because promotion invalidates their original session. Have the owner create distinct synthetic employee invites in the app.

## Cost and daily checks

For 50 users at 10 foreground minutes per day and a 60-second poll interval, plan for about **45,000–50,000 API requests/month** including routine auth and worklog activity. The polling baseline alone is 50 × 10 × 30 = 15,000 reads. The estimate leaves room for initial loads, writes and browser CORS preflights, which are proxied by this gateway. Count actual gateway requests and function calls after rollout. Each API request can use multiple YDB operations. Foreground usage and retry traffic can change the estimate.

Before creating resources, price Gateway requests, Functions invocations and execution time, YDB request units and stored bytes, Object Storage requests and stored bytes, KMS and logs for the approved region and billing account. Allow for the temporary isolated restore and for the backup bucket to hold around 30 full snapshots. Free allocations depend on the account and services. Leave YDB provisioned throughput at **0 RU/s**. Set the per-database storage limit to **1 GB** if supported and set a measured consumption-rate limit that allows shared-IP sign-ins and a full backup. These limits restrict storage and request rate. Configure billing alert thresholds with the owner because alerts leave usage running. Exclude provisioned function instances, dedicated capacity and added paid resources from setup unless approved. [YDB limits](https://yandex.cloud/en/docs/ydb/concepts/limits) · [Serverless YDB limits and pricing](https://yandex.cloud/en/docs/ydb/concepts/serverless-and-dedicated) · [Billing budgets](https://yandex.cloud/en/docs/billing/concepts/budget)

For the Russia tariff, budget approximately **3.16 RUB per month per active KMS key version** for a 720-hour month (720 × 0.00439 RUB). Cryptographic operations are billed separately. Verify the tariff for the approved region and billing account and obtain owner approval for the KMS spend before creating the key. [Official KMS pricing](https://yandex.cloud/ru/docs/kms/pricing)

Allow up to 10 minutes per day to check the latest manifest, backup duration/failures, app 5xx and throttling, consumed YDB RUs and storage, function billed duration, and spend against alerts. Measure these during a 50-account synthetic test with users signing in through one workplace-style shared IP. Confirm normal login reaches all 50 accounts and auth abuse still hits the per-email and per-IP limits. Repeat backup and restore with representative worklog sizes. Pause the pilot if real usage consistently exceeds the approved budget or limits.

## Backup and isolated restore rehearsal

The exporter uses one YDB snapshot-read transaction with keyset pagination. The payload and manifest are written to a fresh UTC date/UUID path. Each upload is conditional and KMS-encrypted over HTTPS. The manifest is the completion marker and gives the schema version, UTC time, source database path, object paths, per-table row counts and SHA-256 of the payload. Keep bucket access restricted to approved identities because the data includes email addresses, worklogs and password hashes.

The backup keeps account roles, invites, worklogs and revisions, mutation receipts and audit events. It excludes session and reset records and transient rate limits. Restore revokes invitations that were still available at the backup time and preserves used and revoked states. It rebuilds the email lookup and commits atomically after validating the snapshot and checking all target tables are empty. The pilot snapshot bounds are 36 MiB and 75,000 records. If either bound is reached, the backup fails and alerts. Review measured volumes and YDB transaction limits before increasing them. The checksum detects corruption. Integrity of the manifest itself depends on bucket access and the trusted writer.

1. Start with two synthetic users. Verify owner/employee roles, authorized reads and rejected cross-user writes. Save a worklog, issue an invite and capture a daily backup, then consume that invite on the source. Exercise both valid and invalid credential paths, app-side sync and the one-use invitation race. Check a direct anonymous function invocation and backup gateway path are rejected and an anonymous bucket list/read receives access denied.
2. Following owner approval for the temporary database, create a separate disposable serverless restore database and apply the same schema. Keep it disconnected from gateways, functions, timers and live users. Verify its resource ID and path against the console. Use an identity which can write only to that target, with no write access to the source or legacy resources. Run the restore with the manifest key observed in the approved bucket. Obtain an IAM token for the restore identity through the CLI or approved impersonation and supply it via environment variable. Turn off shell tracing and clear the token after use.

   ```bash
   python -m backend.backup \
     --bucket "$APPROVED_PILOT_BACKUP_BUCKET" \
     --manifest-key "$COMPLETE_MANIFEST_KEY" \
     --endpoint "$RESTORE_YDB_ENDPOINT" \
     --source-database "$PILOT_YDB_DATABASE" \
     --restore-database "$ISOLATED_RESTORE_YDB_DATABASE" \
     --confirm-isolated
   unset WORKLOG_RESTORE_IAM_TOKEN
   ```
3. Compare the restored counts with the manifest and verify worklog ownership, contents and revision, owner/employee roles, and sign-in with both synthetic passwords using the backend against the isolated target. Confirm old access/refresh and reset tokens fail. Confirm the code consumed after capture and all other old unused codes fail, and that used invites retain their state. Confirm a second import to the populated target fails. Record elapsed time, measured RU, and verification outcomes without including values from tokens or records. A successful hosted rehearsal is required before any real data goes into the pilot.

## Teardown

If a smoke test fails or the pilot ends, disable the pilot gateway and timer to stop new traffic. Remove only the approved pilot functions, identities and test databases, including the disposable restore database. Keep retained backup objects private for the agreed retention period, then remove the pilot bucket and schedule deletion of the dedicated key after approved backups expire. Recheck the existing `worklog-api` identifiers, bindings and backup schedule. Confirm no pilot resources keep accruing unexpected charges.

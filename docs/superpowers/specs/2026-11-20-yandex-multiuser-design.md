# Worklog Yandex test — design

## Intent and scope
The owner primarily uses Worklog himself and may distribute APKs to a few work colleagues. Keep the confirmed Firebase test build #28 and main branch unchanged. Build independently in `worklog-yandex-test` based on f0eb93b7d053b2d8b75685ee273dbed4abfa6d06. Use a distinct Android application ID `com.worklog.app.yandex.test` and label `Worklog Yandex Test`; only synthetic data until end-to-end checks pass. No marketplace submission, automatic real-data/account migration, or unapproved paid provisioning. Existing accounts and passwords remain in Firebase; new test accounts are separate.

## Approaches and choice
- Continue Firebase: fastest, already working; does not achieve the desired Yandex backend. Keep #28 as a fallback.
- Yandex as a backup only: reuses the earlier private function, but leaves primary records in Firebase and does not provide multi-user access control.
- Selected: YDB Serverless for application data and private Cloud Functions behind API Gateway; Object Storage for backups. Preserves the APK workflow and keeps the new environment separate. Public gateway is only a transport endpoint; all protected actions require application-level identity and authorization, with no cloud keys in the APK. Existing private `worklog-api` and bucket must not be made public or changed in a way that breaks previous backups.
- Invitation approaches: a shared reusable code is simple but can be forwarded indefinitely; single-use codes can be individually revoked, expire, and are consumed atomically. User chose single-use. Registration can later be opened intentionally via server configuration; initial mode is closed.

## User experience and access
Keep the existing shifts calendar, settings, totals, individual pay rates, admin-only Employees tab, light/dark theme and JSON export/import. New login remains email/password; registration adds an invitation input. The administrator can create a code, copy it, see available/used/expired/revoked states and revoke unused codes. Default seven-day expiration; high-entropy random human-copyable code (at least 128 bits), no plaintext retained server-side after initial display. Staff cannot create invites or read other users' data. Admin can view other staff's records read-only and edit only their own shifts/settings. Admin role is assigned securely out-of-band to the initial owner after verified account bootstrap, never by an email string or an APK field or open registration. First admin uses a privately supplied one-time bootstrap invitation set by project owner via a privileged setup procedure. No real credentials in git. For this small closed pilot, password recovery uses an owner-assisted one-time reset token provided privately after identity verification; admin cannot see passwords, resets do not silently grant roles, all previous sessions are revoked on reset. No external email service until explicitly configured. Existing #28 authentication is unaffected.

## Backend and security
Use Python Cloud Functions, YDB SDK, serializable read-write transactions for unique normalized email, invitation consumption plus account creation, reset consumption and optimistic writes. Use mature Argon2id password hashing library with per-password salt; never store cleartext passwords, codes or session tokens. Random expiring opaque bearer tokens stored as digests, short-lived access plus bounded revocable session renewal, server resolves account ID and role on every privileged call. Validate payload sizes, date/money/settings types; parameterized queries; generic auth errors, per-email/IP throttling and bounded rate limits to protect costs; no secrets or sensitive payloads in logs. Admin access to other users is read-only even via direct API calls. HTTPS only; narrow CORS for actual Capacitor origins; native secure token storage or session-only fallback, no passwords persisted. Revoke token on signout, isolate and clear user caches when switching users. No cross-account write endpoints. Request authentication before accessing data or backing it up. Provision least-privilege service accounts for gateway invocation, DB access and backup write; protect separate backup service and restore procedure. Do not deploy public gateway until auth and negative tests pass.

## Data model and API
YDB tables: accounts (UUID, normalized email unique lookup, password hash, role, enabled, timestamps); invitation digests and state/expiry/issuer/consumer; session and reset digests with expiry; worklogs keyed by owner UUID (validated version-one personal settings and calendar data with revision and updated timestamp); rate limits; minimal security audit events with no secrets. Keep the current JSON representation for import/export compatibility. API: register, login, renew, logout, password-reset redeem; GET/PUT own worklog; read-only employee list and detail; admin create/list/revoke invites and issue reset. Caller identity for own records always comes from token. Reset and invitation consumption transactional. Initial server snapshot seeds own local cache; authenticated device updates send expected revision and idempotency metadata; reject stale revisions instead of overwriting another device. Show clear conflict message and fetch latest, preserve unsent local copy for recovery, never silently lose shifts. Offline editing and a per-user pending queue sync on reconnect; dashboard read-only offline cached data must remain scoped to account. No Firebase writes from new build. Empty server snapshot is not overwritten automatically by a previous account's cached data.

## Backup, testing and rollout
Private new backup prefix or separate bucket with restricted access; scheduled daily encrypted-in-transit snapshot of YDB application tables and password hashes, but exclude active sessions/reset plaintext (no plaintext secrets exist). Keep a bounded 30-day rotation, retain manual JSON export, monitor failures and billing. Test restoration in an isolated database; verify account/shift linkage, role, and used-code states, invalidate sessions and avoid reopening consumed invites on restore. Budget alerts and quotas, review projected pricing before enabling external resources; no assumption costs are zero. Keep existing private diagnostic function unchanged, use a separate new application function and least-privilege identities. Deployment follows distinct test DB, gateway and build environment, then owner and two fake test accounts, then real pilot only after owner acceptance and privacy readiness. On phone install beside #28; verify own and colleague shifts, code re-use rejected including concurrent registration, invalid/expired/revoked codes rejected, no register bypass, no privilege escalation/cross-account read or write, multi-device sync/offline conflict, reset and logout, backup restore, old APK untouched. Unit tests, real YDB integration tests for race/transactions, smoke test deployed endpoint and signed APK before handing off. Deliberate data import (per-account exported JSON) only after user approval; no account migration or automatic copying from Firebase. Marketplace preparation excluded.
